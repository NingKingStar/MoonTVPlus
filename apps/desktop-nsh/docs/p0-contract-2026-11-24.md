# P0 桌面客户端 · 隔离实例真实契约报告

日期：2026-11-24（Asia/Shanghai）
客户端：`apps/desktop-nsh`（moontv-native 0.3.0，HEAD `5b132342e7d36282e67edd73d188468d8c446ac6` 工作区）

|一侧|事实|

## 怎么复现

```powershell
# 依赖：node_modules 已安装；cargo 1.100.0 在 PATH（本机在 .tools 下）
node apps/desktop-nsh/tests/contract/isolated-run.mjs
```

脚本会：起夹具源 → 用 `scripts/init-sqlite.js` 建一次性库 → 第一次启动实例生成默认配置 → 改写该库的来源配置 → 重启 → 跑 38 项 HTTP/SSE 检查 → 用 `cargo test --test live_contract` 跑客户端真实请求链 → 写报告 → 关掉全部进程。
证据默认留在 `%TEMP%\moontv-nsh-contract-<stamp>\`（`report.md`、`report.json`、`logs/`、`data/moontv.db`）。

不设置 `MOONTV_CONTRACT_BASE` 时，`tests/live_contract.rs` 会直接跳过，所以 `cargo test` 在离线环境仍然是绿的。

## 这一轮发现的真实差异（按影响排序）

1. **集表只认 `.m3u8`**。`src/lib/downstream.ts` 对 `vod_play_url` 的解析要求每集以 `.m3u8` 结尾，纯 MP4 的单集条目在搜索阶段就被丢弃（C10），详情阶段会报“详情没有可用剧集”（C15）。客户端不能把“搜不到”当成源故障，也不能指望 MP4 直链源可用。原生播放器本身能播 MP4，问题在服务端集表协议。
2. **`source-detail` 不返回逐集 headers**。本版服务端只在“脚本源 + `format=json`”路径给 `{url, headers}`；普通采集源的 headers 由服务端代理承担。客户端的 `episode_headers` 目前对普通源是空表，播放时依赖站内代理或直链，不伪造 headers。
3. **上游失败在 SSE 里不可区分**。`searchFromApi` 内部吞掉异常返回空数组，所以 500 的源表现为 `source_result`（空）而不是 `source_error`；`source_error` 只在超时/意外抛出时出现（C18b）。SRC-02 的“源错误”展示需要客户端自己按“空 + 耗时”推断，或服务端补字段。
4. **`origin` 不入库**。`play_records` 只持久化固定列（title/source_name/cover/year/index/total_episodes/play_time/total_time/save_time/search_title/is_anime/is_duanju），`origin` 被丢掉（C24）。直播记录靠 `live_<key>` 的 source 前缀区分，客户端已按这个前缀过滤（`api::progress_from_map`），否则网页端的直播历史会被当成剧集历史导入。
5. **刷新只延长 access**。服务端 `/api/auth/refresh` 不检查 access 年龄，只看 `refreshExpires` 和 refreshToken 是否在存储里；成功时返回同一个 `tokenId`/`refreshToken`/`refreshExpires`，只换 `timestamp` 和签名（C27–C29）。客户端“4 小时 + 提前 10 分钟续期、60 天硬上限”的判断因此是客户端侧的单次合并逻辑，服务端不会帮你挡。
6. **签名没有被业务路由校验**（观察，不是本轮改动）。`getAuthInfoFromCookie` 只解析 token JSON 并检查失效表，不验证 `signature`；也就是说带正确结构的伪造 token 能过鉴权。这是上游既有行为，影响面超出桌面端 P0，记录给服务端安全项（AUTH）单独处理，没有在本轮修改服务端。
7. **`d1`/SQLite 也能刷新**。refreshToken 存在 D1Storage 的 `RedisHashAdapter` 里，所以自建 SQLite/Docker 部署不是“只能 localstorage”的降级路径；`sync_supported()` 为真。

## 本轮为对齐契约做的客户端改动

|改动|原因|
|---|---|
|`api::progress_from_map` 额外跳过 `live_` 前缀的 source|服务端不保存 `origin`，直播记录只能靠前缀识别（发现 4）|
|启动时显式指定 `data_dir`（`MOONTV_DATA_DIR` 可覆盖，默认 `%APPDATA%\MoonTVPlus\nsh`）|不指定时 runner 没有可写目录，设置与收藏/历史只存在内存，重启即丢；已用“关闭再打开”验证持久化|
|历史行增加「已同步 / 仅本机 / 本机」标记，并改掉“播放记录接口未接入”的旧文案|收藏已有一致的标记，历史原先没有，会让人以为不能同步|
|收藏页与首页的“同步未实测”文案改为现状描述|契约已验，旧文案会在界面里继续否认已有能力|
|本机设置/库的存储键改为 `moontv.nsh.*`|开发宿主默认把数据写在同一个目录，与参考工程同名键会互相读到；加产品前缀避免继承别人的库|
|侧栏版本号改为读取 `CARGO_PKG_VERSION`|原来硬编码 “0.2”，与 0.3.0 不符|

## 仍未验证（不要当成通过）

- 真实部署实例（HTTPS、反代、子路径、真实账号组与片源授权）。
- Turnstile 实例：客户端明确报“不能用原生绕过”，没有验证安全浏览器回传。
- 真实第三方片源：只验证了服务端契约与受控夹具。
- 真实第三方片源的音画：演示媒体已经在窗口里播过（见截图 `06-player.png`，00:05/00:30），但声道与听感、硬解、seek 精度、切源、连播人工验收未做。
- Linux 桌面、多屏、混合 DPI、硬件解码、休眠恢复。
- 干净目标机安装/解压启动、签名、自动更新。
- 并发冲突：settings 的 409 分支、两端同时改同一收藏/记录时的合并顺序。

## 界面回归（2026-11-24，同一构建）

窗口截图见 [`docs/screenshots/`](screenshots/README.md)：连接、未连接首页、演示首页、搜索、详情、播放、收藏、历史、设置、重启后首页。播放页截到真实受控 MP4 在播（时间码 00:05 / 00:30，暂停/±5s/静音/全屏控件，标题旁「已收藏」）。

界面里发现并修掉的两件事：

1. **本机记录重启即丢**。runner 在 `data_dir = None` 时没有可写目录，`Storage::set_item` 失败只留内存；已改成启动时显式给 `MOONTV_DATA_DIR` 或 `%APPDATA%\MoonTVPlus\nsh`，并用“关闭-重开”验证收藏与历史仍在（`10-restart-home.png`、`07-favorites.png`）。
2. **界面文案继续否认已验能力**。首页/收藏页仍写“实例同步未验证”“以每张卡的状态为准”；已改成“收藏先写本机；连接实例后尝试同步，状态逐条标注”。

行为边界（按实际按钮而非预期写的）：Esc 只退出全屏，退出播放器要点头部「返回」；收藏卡片为 2:3 竖版，固定窗高时同步标记需要向下滚动才能看到（页面可滚动，截图为滚动后）。
