## 这一轮发现的真实差异（按影响排序）

1. **搜索历史返回裸数组**：`GET /api/searchhistory` 是 `string[]`，POST 也返回更新后的数组；不是 `{history}` 包一层。客户端按数组解析，服务端未确认时保留本机缓存。
2. **建议是 `{suggestions:[{text,type,score}]}`**，且只搜“首个可用源”；空查询直接返回空数组。客户端把它当辅助信息：失败或超时不清空输入、不阻塞搜索。
3. **豆瓣分类与推荐是两套参数**：`categories` 用 `kind/category/type/limit/start`（电影 `category=热门|最新|豆瓣高分|冷门佳片`，剧集/综艺 `category=tv|show`，`type` 是二级值）；`recommends` 用 `kind/limit/start/category/format/region/year/platform/sort/label`，`all`/`T` 由服务端转空。原生“全部”走推荐，“热门/最新/高分/冷门”走分类，两者不能混用。
4. **筛选值要传中文标签**：类型/地区/年代/平台在客户端存英文 id，请求时按网页同款映射成中文（如 `comedy`→`喜剧`、`2020s`→`2020年代`）；直接把 id 传给服务端会让豆瓣返回空。
5. **服务端有搜索缓存**：同一 `q` 第二次 SSE 会立刻返回（首个查询的慢源不再慢）。契约测试用未查询过的关键词测量增量；客户端 UI 不受影响，但仍会按源展示“已完成 x/y”。
6. **Bangumi 日历走实例配置的 base URL**：`SiteConfig.BangumiApiBaseUrl` 可以被隔离实例指向本地夹具，客户端只调 `api/bangumi/calendar`，不直连 `bgm.tv`。
7. **豆瓣海报可能无 Referer 而回落到标题卡**：客户端从不伪造图片；卡片显示“豆瓣”字样的降级样式。真实实例若配置了图片代理，会走代理 URL。
8. P0 的 `.m3u8` 集表规则不变：搜索阶段仍会丢弃只有 MP4 的条目；本轮没有改服务端。

## 仍未验证（不要当成通过）

- 真实部署实例：HTTPS、反代、子路径、真实账号组、片源授权、生产数据。
- 豆瓣不可达/限流时的真实降级：契约里以 skip 记录外部失败，没有模拟长时间 429/封禁。
- 真实第三方片源的搜索结果与 SSE 时序：只用本地夹具和慢源。
- 真实 Bangumi 上游（`bgm.tv`）与本仓配置的多种数据源模式：只验证了 `server-proxy` + 本地 base URL。
- 原生 UI 的播放/音画/seek/连播、键盘矩阵、多屏/DPI、Linux、干净目标机、签名与更新：沿用 P0 的未验证清单。
- 分页只验证到第 2 页（50 条）与客户端去重；没有穷尽豆瓣末页/空页的所有组合。
